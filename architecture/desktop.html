R3 Recovery Services / Application architecture

Windows runtime

One local service serves both the built frontend and API.

Launch and hosting

The ordinary Windows checkout path uses the current-user launcher. Prepared releases include built frontend assets and must not require administrator access, Docker, PostgreSQL, Git, Node.js, or command-line work for normal use.

  • scripts/Start-IZ-Clinical-Notes-Analyzer.cmd
  • scripts/start-windows-local.ps1
  • backend/app/desktop_main.py
  • backend/app/desktop_runtime.py
  • backend/app/desktop_runtime_host.py
  • backend/app/desktop_runtime_control.py

desktop_main serves packaged app/static when present, otherwise frontend/dist. Assets are mounted at /assets; HTML entry points include / and /desktop/{requested_path}. The /api-configuration page points operators to the in-app harness.

Installation and maintenance

Package-root Launch delegates to the installed current-user launcher and instructs the operator to run Install when no install exists. Maintenance and recovery behavior are documented separately.

docs/windows-cmd-maintenance.md backend/app/desktop_maintenance.py

Validation scope

This documentation change does not rebuild or qualify a Windows installer. Application checks are backend pytest, frontend Vitest/build, and relevant Windows smoke / maintenance checks. Packaging requires scans of both the release directory and ZIP.
