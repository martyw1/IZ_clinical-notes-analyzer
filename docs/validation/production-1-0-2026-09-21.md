# Production 1.0 validation — September 21, 2026

Candidate: `1.0.0`, build `2026.09.21.2`, installer revision `1`, channel `stable-local-desktop`. The V2 implementation, local-client deployment mode, and schema 12 remain in use. This document records observed evidence; version metadata does not itself certify deployment readiness.

## Scope and discovered defects

The beta build was paused at the user's request. Work continued toward a distinct production 1.0 package with machine-independent first-use administration, forced password change and recovery, portable extraction, and safe forensic diagnostics.

- OneDrive-backed source folders were rejected by installed/data-root reparse checks. A read-only source staging boundary now validates every manifest member before dispatch; destination and ownership checks remain strict.
- Authentication returned distinct inactive/locked failures, repeated a bootstrap-completion event, and local recovery did not invalidate the previous recovery code atomically with its audit. The updated flow uses generic login failures and safe detailed administrator diagnostics.
- Alleva jobs lacked consistent correlation and request-stage context; completion audit included updated external plan IDs. New diagnostics record safe categories, counts, durations, attempts, HTTP statuses, and job IDs.
- A complete client reconciliation changed unlinked-plan placeholders to missing patients. This caused six historical placeholders with nine plans to appear in the development Patient Roster even though their plans remained correctly unlinked. The repair preserves all plans and genuine missing patients. Linked plan persistence also preserves inactive and discharged client states instead of overwriting them as active.
- The live verifier omitted exact plan-version/record selectors and mixed source identities. It now follows the product UI's explicit selection contract, preserves intentional HTTP 409 ambiguity protection, and uses Windows PowerShell 5.1-compatible Python transport.
